# Module Review Rubric

Verifier 评分判据。7 维各 1-5 分;PASS 要求全部 ≥3、逐模块 verdict 全 PASS、
cross_review 通过、无 BLOCKING 发现、五门禁全绿。

## 分数通用定义

| 分 | 含义 |
|---|---|
| 5 | 该维度不仅合规,还给下游额外提供了可执行的确定性(如失败处理写到可直接转化为测试用例) |
| 4 | 合规,无实质问题 |
| 3 | 合格底线:有交代但存在可改进处,不影响下游开工 |
| 2 | 有缺口,下游开工后会在此维度返工 |
| 1 | 缺失或错误,照此开发必然出错 |

## 七维判据

### 1. architecture_conformance(架构承接)
- 5:职责/依赖/数据/暴露忠实承接,exposes 条条落点清晰,交互承接与架构关键交互表一致,映射表可直接反查
- 3:承接成立但个别落点牵强(expose 塞给不相关组件)
- 1:快照漏抄架构声明(分母造假)、私自扩边、exposes 无落点、改写职责语义

### 2. internal_clarity(内部结构清晰)
- 5:每个组件单一职责可陈述,核心流程沿组件边界走得通,规模适中,组件划分经得起"为什么不是另一种切法"追问
- 3:结构成立但有模糊地带(两组件职责有重叠措辞)
- 1:god-component 苗子、流程绕过组件边界、模块规模失控(应回架构拆模块)

### 3. information_hiding(信息隐藏)
- 5:每个组件 hides 写实(隐藏了什么设计决策),对外只经架构 exposes 触达,无数据泄漏
- 3:隐藏成立但个别 hides 复述职责或空泛
- 1:内部组件直接对外服务、模块内数据泄漏、hides 逐条凑数

### 4. tradeoff_honesty(取舍诚实)
- 5:每条取舍的 cost 具体到"放弃了什么能力/承担了什么复杂度",替代方案有排除理由
- 3:取舍成立但个别 cost 是换汤话术("牺牲了一点灵活性")
- 1:关键内部决策无取舍记录、cost 为空话术、只写收益不写代价

### 5. dfx_readiness(DFX 与失败准备)
- 5:五项 DFX 条条落到组件/机制/参数,FMEA 覆盖全部核心组件且失效模式真实,可测试性有具体测试接缝
- 3:DFX 有落点但长尾场景(部分失败、恢复中途)含糊
- 1:DFX 口号化、FMEA 缺失或走形式(只列人为失误)、失败处理整体缺失

### 6. simplicity(简单性)
- 5:每个内部复杂度机制(队列/缓存/状态机/后台任务)点名可溯源的真实问题;更简单的内部结构被明确考虑并记录排除理由
- 3:复杂度有理由但个别论证牵强("未来可能需要")
- 1:无问题背书的机制堆叠;存在明显更简单的内部结构且无排除记录;多模块各自重复发明同一机制

### 7. traceability(溯源)
- 5:关键陈述条条有 Ledger 背书,FACT 指向架构产物/代码可验证,DECISION 有拍板锚点,INFERENCE 依据链成立
- 3:主要决策有溯源,边缘陈述裸奔
- 1:架构声明无溯源、DECISION 无锚点、把推断写成事实

## 对抗 7 维定义(self_challenge 共用)

| 维度 | 攻击问题 |
|---|---|
| failure_modes | 每个外部依赖、消息、后台任务的丢失/重复/延迟时,模块内部会发生什么? |
| consistency | 本模块自有数据的内部一致性(缓存 vs 持久化、状态机转换)哪里会泄漏为错误行为? |
| concurrency | 模块内竞态、双写、丢失更新、缺失幂等在哪里发生? |
| boundary_erosion | 哪个内部组件会积累职责成为下一个 god-component? |
| hidden_coupling | 有没有绕开架构声明的隐式依赖(共享存储/时序先后/读别人的表)? |
| testability | 每个核心流程能被独立测试吗?测试接缝在哪里? |
| simpler_alternative | 有没有实质上更简单且同样承接架构的内部结构? |

## Cross 检查定义(全部模块 PASS 后)

| 检查 | 攻击问题 |
|---|---|
| 交互对齐 | 两个模块对同一架构交互的承接描述矛盾吗?参与方都认领了吗? |
| 机制重复 | 多个模块各自实现了同一机制(重试/缓存/幂等/通知)而互相不知情? |
| 概念漂移 | 同一概念(状态枚举/字段语义/时间戳约定)在不同模块里定义一致吗? |

## Severity 定义(critical_issues / findings / cross findings 共用)

| 级 | 含义 |
|---|---|
| 🔴 BLOCKING | 照此开发必然返工/翻车,必须先解决 |
| 🔴 HIGH | 上线后高概率出事或显著浪费,交付前必须解决 |
| 🟡 MEDIUM | 特定条件下出事,应解决或明确接受为风险 |
| 🟢 LOW | 改进建议,不阻塞 |
