# 拆解质量评审量规

> 上游输入统一称 `spec_source`(工程 Spec 优先,已批准 PRD 亦可)。文中凡说"需求""PRD",
> 都读作 `spec_source`。缺口浮出后交用户三选一,不是静默硬停。

**使用方**:Verifier(独立评审)、Executor(交预览前的自检)
**用途**:在渲染 output/ 之前判定目录质量
**配套**:产出格式见 `agents/verifier.md` 与 `schemas/verification.schema.json`——
**本文件只定义"怎么判",不定义"输出长什么样"**(契约只在一处定义)

---

## 严重度分级

| 级别 | 含义 | 动作 |
|---|---|---|
| **BLOCKING** | 不修就无法继续 | 交付前**必须**修 |
| **HIGH** | 重大质量问题 | 交付前**必须**修 |
| **MEDIUM** | 质量隐患 | **应当**修,时间紧可讨论 |
| **LOW** | 可改进 | 可选,记入精修 |

---

## 七个评审维度

### 1. 覆盖 Coverage

| 判据 | 严重度 | 检查 |
|---|---|---|
| 上游每条显式需求都有落点 | BLOCKING | 每条需求映射到 ≥1 个 story |
| 不超出上游凭空发明 | BLOCKING | 每项溯源到 `spec_source` 的规则(FACT)或用户决定(DECISION);溯不到的删除或浮出为缺口 |
| 无未解释的空档 | HIGH | 现状与目标之间没有说不清缺失的功能 |
| 范围边界清楚 | MEDIUM | In Scope / Out of Scope 都有记录 |

清单:

- [ ] 需求里每一句都映射到 ≥1 个拆解项
- [ ] 无上游溯源(FACT/DECISION)的项被删除或浮出为缺口——**绝不作为"隐式需求"保留**
- [ ] 上游沉默、且无用户 `DECISION` 的风险类 → 浮出为缺口;覆盖从不凭空补齐
- [ ] Out of Scope 项显式记录

### 2. 粒度 Granularity

| 判据 | 严重度 | 检查 |
|---|---|---|
| Epic 是业务能力规模 | HIGH | 周到月,不是"加个按钮" |
| Feature 是功能域规模 | HIGH | 天到周,不是"把整个系统建出来" |
| Story 是用户价值增量,≤8 故事点,过 INVEST | HIGH | 13+ 必须拆(见本文件「Story 规模纪律」) |
| 没有大到估不出点的项 | HIGH | 全部可估(T 恤码或故事点) |

清单:

- [ ] 没有"实为 Feature"的 Epic
- [ ] 没有"实为 Story"的 Feature
- [ ] 每个 story ≤8 点、过 INVEST、验收标准数量达规模底线
- [ ] 没有"杂项""其他"这类项

### 3. 层级 Hierarchy

| 判据 | 严重度 | 检查 |
|---|---|---|
| 父子关系合法 | BLOCKING | 无环、无孤儿 |
| 嵌套深度合适 | HIGH | Epic 之下最多 3 层 |
| 每个 Epic 有 ≥1 个 Feature | BLOCKING | 无空 Epic |
| 每个 Feature 有 ≥1 个 Story | BLOCKING | 无空 Feature |

清单:

- [ ] 无孤儿项
- [ ] 无循环父子关系
- [ ] ID 遵循 `EPIC-e → FEATURE-e.f → STORY-e.f.s`
- [ ] 无 0 Feature 的 Epic、无 0 Story 的 Feature
- [ ] 跨切关注点被提到正确的层级

### 4. 完整度 Completeness

| 判据 | 严重度 | 检查 |
|---|---|---|
| Epic 有成功标准 | HIGH | 可度量的业务结果 |
| Feature 有范围说明 | MEDIUM | 包含什么 |
| Story 有验收标准 | HIGH | 数量达规模底线(见本文件「Story 规模纪律」) |
| 依赖已记录 | HIGH | 产品级依赖全部落图 |

清单:

- [ ] 每个 Epic 有可度量的成功标准
- [ ] 每个 story 的验收标准数量达标(3-4 / 4-6 / 5-8)
- [ ] 依赖带类型(`blocked-by` / `related-to`,仅此两类)
- [ ] 风险与假设已记录

### 5. 可执行性 Actionability

| 判据 | 严重度 | 检查 |
|---|---|---|
| Story 用"作为…我希望…以便…"表述 | HIGH | 标准用户故事格式 |
| 每项范围清晰到**可指派给单一负责人** | HIGH | 不存在职责共担的模糊项 |
| 已定优先级 | MEDIUM | 全部 P0-P3 |

清单:

- [ ] Story 是用户故事格式
- [ ] 每项边界清楚,不需要多人共担
- [ ] 优先级已定且给了理由
- [ ] 需要跨团队协调的项已注明

**注意**:这里判的是"**能不能**被单一负责人接走",不是"**由谁**接"。实际指派是下游
`planning-and-task-breakdown` 的事,目录里给 owner 属于越界。

### 6. 场景覆盖 Scenario Coverage

| 判据 | 严重度 | 检查 |
|---|---|---|
| 两级表态完整 | BLOCKING | 全局 `category_defaults` 划得合理(全局豁免有项目级理由),story 偏离结构合法(R5 通过只是底线) |
| 排除理由具体 | BLOCKING | `inapplicable`(全局/story)理由分级具体:全局写项目级原因,story 写本 story 原因,不是"不适用"这类空话 |
| 沉默豁免审过 | BLOCKING | 逐 Story 扫未决类别:该适用却被沉默掉的(如支付 story 对 boundary 缄默)没有被放过 |
| 覆盖可度量 | BLOCKING | 分子、分母、百分比、排除项齐全,且**来自脚本计算** |
| 场景类别覆盖 ≥90% | BLOCKING | `scenario_category_pct` |
| 关键风险覆盖 =100% | BLOCKING | P0/P1 的 security / authorization / funds / privacy / irreversible / data_integrity |
| 覆盖声明与场景对应 | BLOCKING | 声明的风险类必须真有场景在 `covers` 里写了它 |
| 缺口有处置 | HIGH | 变成场景,或记录为显式 `DECISION` |
| 场景不重复 | MEDIUM | 等价类与边界值不产生组合噪音 |

清单:

- [ ] 每个 story 至少一个 normal 场景,或有正当的非用户可见理由
- [ ] 每个适用的异常类都有场景
- [ ] 存在上限/下限的地方,评估了边界与边界外一点
- [ ] 沉默豁免(全局与 story 都未声明的类别)逐 Story 审过——该适用却被沉默的没有放过
- [ ] `inapplicable` 的排除理由分级:全局是项目级、story 是 story 级,均非空话
- [ ] 90% 这个数字标注为"场景类别覆盖",不是代码覆盖

**两个百分比照抄 `validate.py` 打印的值填入 `coverage`**(自己算的数会被 R6 逐位比对打回)。
Verifier 真正要动脑的是:**两级声明划得对不对**——全局豁免有项目级依据吗?该适用的漏标或
被沉默了吗?不该适用的被塞进来注水了吗?分母是唯一可被操纵的地方,全局豁免是最大的操纵面。

### 7. 可溯源 Traceability

| 判据 | 严重度 | 检查 |
|---|---|---|
| 每项有稳定锚点 | HIGH | `trace` 指向 `spec_source` §x 或 DECISION 锚点,不是自造 ID |
| Story 能溯源到需求 | BLOCKING | 无不可溯源 story,无遗漏需求 |
| 场景能溯源到验收标准 | BLOCKING | 每个场景至少证明一条验收标准 |
| Ledger 与目录一致 | BLOCKING | `type=FACT|DECISION` 的条目都有非空 `evidence` |

清单:

- [ ] 需求 → story → 验收标准 → 场景 链路完整
- [ ] 无投机项缺少可溯源的需求或风险依据

## Story 规模纪律

故事点用斐波那契。**超过 8 点的 story 是"捆了多个用户价值"的味道。**

| 故事点 | 验收标准下限 | 规则 |
|---|---|---|
| 1-2 | 3-4 条 | 细粒度 story |
| 3-5 | 4-6 条 | 典型 story |
| 8 | 5-8 条 | 上限——必须重点审是否有可拆之处 |
| 13+ | — | **必须拆**;`artifact.schema.json` 只放行 1/2/3/5/8 |

## INVEST 校验(每个 story,进预览前)

| 判据 | 问句 | 通过条件 |
|---|---|---|
| **I**ndependent 独立 | 不依赖其他未承诺的 story 也能验收? | 无未标注或未落图的阻塞依赖 |
| **N**egotiable 可协商 | 说的是 WHAT 不是 HOW? | 纯产品行为,无实现细节 |
| **V**aluable 有价值 | 交付用户可见价值? | 有清晰、用业务语言写的"以便" |
| **E**stimable 可估 | 团队能估点? | 范围与场景类别都清楚 |
| **S**mall 小 | 一个迭代能完? | ≤8 故事点 |
| **T**estable 可测 | 能验证做完了? | 验收标准达下限 + 场景类别已枚举 |

**任一条不过,就回到拆分技法重做——不带着不合格的 story 进入场景枚举阶段。**

## 评分

每个维度 1-5 分:

| 分 | 含义 |
|---|---|
| 5 | 优秀——无需改进 |
| 4 | 良好——有小改进空间 |
| 3 | 合格——达到最低门槛,仍有改进空间 |
| 2 | 低于门槛——需要显著改进 |
| 1 | 差——需要推倒重做 |

## 通过判定

**PASS** = 七维全部 ≥3 分,且无 BLOCKING 项,且 `scenario_category_pct` ≥ 90%,
且 `critical_risk_pct` = 100%。

**不 PASS** 时按问题的**归属**分流(与 `agents/verifier.md` 的 verdict 定义一致):

- 问题出在**产物** → `REVISE`,回 Executor
- 问题出在**拆解规划/策略** → `REPLAN`,回 Planner
- **缺口未决**或关键外部信息缺失 → `BLOCKED`,进 `WAITING_FOR_INPUT`

迭代上限由 `state.max_iterations` 决定(**不硬编码次数**)。超出即停止,并明确报告:
当前最佳目录状态、未解决的 critical_issues、覆盖率数字、仍未闭环的缺口。**不得宣称完成。**

## 常见质量模式

### 好的模式

- "作为用户,我希望通过邮件重置密码,以便忘记密码时能恢复账号访问"——具体、可测、单一职责
- Feature 范围清楚写明包含什么、不包含什么
- 依赖引用具体 ID 并带类型
- Story ≤8 点,验收标准达下限,过 INVEST
- 场景覆盖写明适用类别、排除项与计算口径
- 边界场景测确切边界与其外最近值

### 有问题的模式

- "用户管理"当一个 Feature(太泛,应拆成 story)
- "修 bug"当一个 Epic(不是业务能力)
- 验收标准写"应该能用"(不可测)
- 一个正常路径 + 一个笼统的"处理错误"场景
- 声称 90% 覆盖但给不出分母
- 拿源码覆盖率当作行为风险已拆解的证据
- 超过 8 点的 story 混进目录——评审前就拆掉
- 实为 Epic 的 story("作为用户,我希望有完整的系统")
- `inapplicable`(全局或 story 级)的理由写成"不适用"
- 全局豁免没有项目级依据,一次豁免让所有 story 免检(最大的分母操纵面)
- 把易覆盖的垃圾类别塞进 `applicable`/`applicable_add` 充数,稀释真实缺口的占比
