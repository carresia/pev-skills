# 任务清单质量评审量规

> 门槛上游统一称 `arch_source`(架构产物或用户架构文档),同轮设计产物为 `aux_sources`。
> 上游层缺口浮出后交用户三选一,不是静默硬停。

**使用方**:Verifier(独立评审)、Executor(交预览前的自检)
**用途**:在渲染 output/ 之前判定任务清单质量
**配套**:产出格式见 `agents/verifier.md` 与 `schemas/verification.schema.json`——
**本文件只定义"怎么判",不定义"输出长什么样"**(契约只在一处定义)

---

## 严重度分级

| 级别 | 含义 | 动作 |
|---|---|---|
| **BLOCKING** | 不修就无法继续 | 交付前**必须**修 |
| **HIGH** | 重大质量问题 | 交付前**必须**修 |
| **MEDIUM** | 质量隐患 | **应当**修,时间紧可讨论 |
| **LOW** | 可改进 | 可选,记入精修 |

---

## 七个评审维度

### 1. 覆盖 Coverage

| 判据 | 严重度 | 检查 |
|---|---|---|
| 范围内工作项条条有任务落点 | BLOCKING | inventory 每条 in_scope 项 → ≥1 任务 `implements`;门禁 100% |
| 不超出上游凭空发明 | BLOCKING | 每条任务溯源到上游产物(FACT)或用户决定(DECISION);溯不到的删除或浮出为缺口 |
| 分母登记完整 | BLOCKING | 上游逐份对照:架构模块、模块设计 exposes、API 契约、库表、Story——上游有而 inventory 没登记的是分母造假 |
| 范围收缩有据 | HIGH | in_scope=false 逐条有理由、有出处,不是"难拆就扔出范围" |

清单:

- [ ] inventory 的每条 in_scope 项映射到 ≥1 条任务
- [ ] 无上游溯源(FACT/DECISION)的任务被删除或浮出为缺口——**绝不作为"合理基建"保留**
- [ ] 上游产物逐份扫过,没有漏登记的工作项
- [ ] 范围外项的理由成立且有留痕

### 2. 粒度 Granularity

| 判据 | 严重度 | 检查 |
|---|---|---|
| 任务四档、files 与档位一致 | BLOCKING | XS=1 · S≤2 · M=3-5 · L=6-8,超 8 必拆(schema 与脚本已拦结构,这里审"划得对不对") |
| L 档逐个审过 | HIGH | 每条 L 档问"还能再拆吗"——拆不动要能说出为什么 |
| 单任务单职责 | HIGH | 标题带"和/and/以及"串两件事、验收标准超 5 条,都是应拆信号 |
| 任务可单会话完成 | MEDIUM | 一条任务一个专注会话做不完,就该拆 |

清单:

- [ ] 没有"实为 PHASE"的任务(捆了一堆文件一个大目标)
- [ ] 没有"实为子步骤"的任务(一个函数改动拆成三条任务凑数)
- [ ] L 档任务逐个有"为什么不能再拆"的答案
- [ ] 没有"杂项""其他""收尾"这类项

### 3. 顺序与切片 Ordering

| 判据 | 严重度 | 检查 |
|---|---|---|
| 依赖图无环、文档序=拓扑序 | BLOCKING | 前置任务排在后继之前(脚本已拦,这里审依赖声明本身对不对) |
| 纵切优先 | HIGH | 阶段交付可运行的价值路径,不是横切大水漫灌 |
| 地基先行 | HIGH | 被依赖最多的任务(数据模型、契约、公共类型)排在前面 |
| 高风险前置 | MEDIUM | 最不确定的任务排前(fail fast),不是留到最后爆雷 |
| 阶段终点是可工作状态 | HIGH | 每个 checkpoint 过后系统可运行、可演示,不是半拉子中间态 |

清单:

- [ ] 每条依赖声明真实(不是"顺手排的顺序")
- [ ] 阶段划分沿价值路径(纵切),横切有 Planner 声明的理由
- [ ] 高风险/高不确定任务前置
- [ ] 每阶段结束系统处于可工作状态

### 4. 可验证性 Verifiability

| 判据 | 严重度 | 检查 |
|---|---|---|
| 每条任务有验收标准 | BLOCKING | 可判定的完成条件,"应该能用"这类空话不算 |
| 每条任务有验证方式 | BLOCKING | verification 能真跑:命令对、manual 写清看什么 |
| 验收标准与验证方式对应 | HIGH | 验收说的和验证查的是同一件事 |

清单:

- [ ] 每条任务的验收标准读完就能判"做完没做完"
- [ ] 每条 verification 拿到就能执行,不需要再想"怎么验"
- [ ] manual 类验证写明看什么、什么算过

### 5. 并行化 Parallelization

| 判据 | 严重度 | 检查 |
|---|---|---|
| 并行组内无依赖路径 | BLOCKING | 脚本已拦;这里审"该并行的没并行" |
| 并行边界有收益 | MEDIUM | 划了组但组内任务都很小,并行开销大于收益 |
| 共享契约先定 | HIGH | 多任务共享的契约/类型/接口,有前置任务先定它 |

清单:

- [ ] 声明的并行组真的可同时动
- [ ] 共享 API 契约/数据模型的任务有明确前置
- [ ] 不确定能并行的没被硬塞进同组

### 6. 检查点 Checkpoints

| 判据 | 严重度 | 检查 |
|---|---|---|
| 每 PHASE 有终点检查点 | BLOCKING | schema 已拦存在性;这里审检查内容覆盖该阶段关键路径 |
| 检查可执行 | HIGH | checks 写命令或可观测判据,不是"确认没问题" |
| 关键里程碑有人审 | HIGH | 该 `review_with_human` 的节点设了;没设的逐个有理由 |

清单:

- [ ] 检查点检查的是本阶段交付的关键路径,不是泛泛的"测试通过"
- [ ] 数据迁移/不可逆操作后有明确检查
- [ ] 关键节点(review 后才许继续)已标记

### 7. 可溯源 Traceability

| 判据 | 严重度 | 检查 |
|---|---|---|
| 每条任务有稳定锚点 | HIGH | `trace` 指向上游产物 §x 或 DECISION 锚点,不是自造 ID |
| 任务能溯源到设计 | BLOCKING | 无不可溯源任务,无遗漏工作项 |
| Ledger 与清单一致 | BLOCKING | `type=FACT|DECISION` 的条目都有非空 `evidence` |

清单:

- [ ] 上游 → inventory → 任务 → 验收标准 链路完整
- [ ] 无投机任务缺少可溯源的设计或决定依据

## 任务规模纪律

四档制,**超过 8 个文件的任务是"捆了多件事"的味道**:

| 档位 | 文件数 | 验收标准 | 规则 |
|---|---|---|---|
| XS | 1 | 1-2 条 | 单函数/配置级改动 |
| S | 1-2 | 1-3 条 | 单组件/单端点 |
| M | 3-5 | 2-4 条 | 一条功能切片 |
| L | 6-8 | 3-5 条 | 多组件功能——必须重点审是否有可拆之处 |
| XL | — | — | **不存在**;schema 拦截,超 8 文件必拆 |

**应拆信号**(任一命中就回拆分技法):
- 一个专注会话(约 2 小时 agent 工作)做不完
- 验收标准写不进 5 条以内
- 触及两个以上独立子系统(如认证与计费)
- 标题里出现"和/and/以及"——那是两条任务

## 拆分技法

| 技法 | 何时用 | 例 |
|---|---|---|
| 按流程步骤 | 线性过程 | "结算" → "加购" + "付款" + "确认订单" |
| 按层内纵切 | 单功能跨层 | "用户注册" → schema + API + UI 一条切片内的三个任务 |
| 按操作 | CRUD | "管理用户" → "新建" + "编辑" + "删除" |
| 按数据类型 | 多种输入 | "导入" → "导入 CSV" + "导入 Excel" |
| 正常路径优先 | 降风险 | 先做基本流程;异常/边缘处理只有在**独立可交付**时才单独成任务 |
| 抽公共前置 | 多任务重复 | 共享的类型/工具/契约先抽成前置任务 |

## 评分

每个维度 1-5 分:

| 分 | 含义 |
|---|---|
| 5 | 优秀——无需改进 |
| 4 | 良好——有小改进空间 |
| 3 | 合格——达到最低门槛,仍有改进空间 |
| 2 | 低于门槛——需要显著改进 |
| 1 | 差——需要推倒重做 |

## 通过判定

**PASS** = 七维全部 ≥3 分,且无 BLOCKING 项,且 `upstream_coverage_pct` = 100%。

**不 PASS** 时按问题的**归属**分流(与 `agents/verifier.md` 的 verdict 定义一致):

- 问题出在**产物** → `REVISE`,回 Executor
- 问题出在**拆解规划/策略** → `REPLAN`,回 Planner
- **缺口未决**或关键外部信息缺失 → `BLOCKED`,进 `WAITING_FOR_INPUT`

迭代上限由 `state.max_iterations` 决定(**不硬编码次数**)。超出即停止,并明确报告:
当前最佳清单状态、未解决的 critical_issues、覆盖率数字、仍未闭环的缺口。**不得宣称完成。**

## 常见质量模式

### 好的模式

- 每条任务拿给一个不熟悉项目的人,读完就知道改哪几个文件、怎么算做完
- 依赖箭头与真实构建顺序一致,阶段终点系统可运行
- 高风险任务(新框架、不确定的集成)排在最前面
- 检查点的检查就是该阶段验收标准的机器化版本
- 并行组里放的是真正独立的功能切片

### 有问题的模式

- "实现整个后端"当一条任务(横切大水漫灌)
- 验收标准写"功能正常"(不可判定)
- verification 全是 manual 且不写看什么
- 任务顺序按目录字母序排,不是按依赖排
- 把最难的部分留到最后(高风险后置)
- inventory 登记一半,漏掉的靠"隐含任务"兜底
- 范围外项没有理由,只是难拆
- 一个检查点管五个阶段(检查粒度和阶段不匹配)
- 拿"任务数多"当覆盖充分的证据——数量不等于对账
