# Architecture Review Rubric

Verifier 评分判据。7 维各 1-5 分;PASS 要求全部 ≥3 且无 BLOCKING 发现、四门禁全绿。

## 分数通用定义

| 分 | 含义 |
|---|---|
| 5 | 该维度不仅合规,还给下游额外提供了可执行的确定性(如失败处理写到可直接转化为测试用例) |
| 4 | 合规,无实质问题 |
| 3 | 合格底线:有交代但存在可改进处,不影响下游开工 |
| 2 | 有缺口,下游开工后会在此维度返工 |
| 1 | 缺失或错误,照此开发必然出错 |

## 七维判据

### 1. upstream_coverage(上游覆盖)
- 5:upstream_items 声明完备且每条落点清晰,映射表可直接反查
- 3:覆盖齐全但个别落点牵强(塞进不相关模块)
- 1:upstream_items 漏声明(分母造假)或 In Scope 条目无落点
- 反向同样扣分:模块无上游依据、无 DECISION、无合理 INFERENCE = 无中生有

### 2. boundary_clarity(边界与依赖)
- 5:每个模块职责单一可陈述,外部依赖全部隔离在边界后,依赖方向经得起"为什么它依赖它"追问
- 3:边界成立但有模糊地带(两模块职责有重叠措辞)
- 1:god-module 苗子、核心域依赖外围、职责重叠无人认领

### 3. ownership(数据所有权)
- 5:每数据唯一 owner,owner 在写方列表,读者/写者与模块能力一致
- 3:所有权成立但个别写方列表与暴露能力矛盾
- 1:共享写无 owner、owner 挂名不在写路径、owner 唯一性破坏

### 4. tradeoff_honesty(取舍诚实)
- 5:每条取舍的 cost 具体到"放弃了什么能力/承担了什么运维负担",替代方案有排除理由
- 3:取舍成立但个别 cost 是换汤话术("牺牲了一点灵活性")
- 1:关键决策无取舍记录、cost 为空话术、只写收益不写代价

### 5. failure_readiness(失败与演进)
- 5:对抗 7 维每个外部依赖/消息/节点的丢失、重复、延迟都有交代,回滚策略明确、容量峰值是否落在规划期内有判断
- 3:主路径有交代,长尾场景(部分失败、迁移中失败)含糊
- 1:最终一致泄漏到用户可见行为且上游未批准、无回滚策略、失败处理整体缺失

### 6. simplicity(简单性)
- 5:每个复杂度机制点名可溯源的真实问题;更简方案被明确考虑并记录排除理由
- 3:复杂度有理由但个别论证牵强("未来可能需要")
- 1:无问题背书的队列/缓存/微服务/CQRS/多库;存在明显更简单方案且无排除记录

### 7. traceability(溯源)
- 5:关键陈述条条有 Ledger 背书,FACT 指向上游/代码可验证,DECISION 有拍板锚点,INFERENCE 依据链成立
- 3:主要决策有溯源,边缘陈述裸奔
- 1:产品级约束无溯源、DECISION 无锚点、把推断写成事实

## 对抗 7 维定义(self_challenge 与 review_findings 共用)

| 维度 | 攻击问题 |
|---|---|
| failure_modes | 每个外部依赖、节点、消息丢失/重复/延迟时会发生什么? |
| consistency | 最终一致在哪里泄漏为用户可见行为?上游批准了吗? |
| concurrency | 竞态、双写、丢失更新、缺失幂等在哪里发生? |
| boundary_erosion | 哪个模块会积累职责成为下一个 god-module? |
| migration_rollback | 每个 schema/发布变更可回滚吗?爆炸半径多大? |
| scale_cliff | 什么负载/数据量下设计失效?规划期内会到吗? |
| simpler_alternative | 有没有实质上更简单且同样满足上游的设计? |

## 评审手法(贯穿各维)

评分锚点之外,三个主动动作;发现按所属维度记入 findings:

1. **静默假设扫描**:设计中隐含而未记录的假设(容量、时序、可用性、一致性、权限
   边界),逐条当发现报出——没有写进 tradeoff / DECISION / INFERENCE 的假设就是
   一条 finding,记 `traceability`。
2. **决策依赖走查**:把设计当决策树过一遍:每个关键决策(风格、模块边界、数据
   所有权)若被推翻,下游哪些模块/交互/取舍跟着作废?作废面大而设计未交代 =
   finding,记 `boundary_clarity` 或 `tradeoff_honesty`。
3. **读文件定不了的转验证项**:性能、实际负载、三方实际行为这类对谈裁定不了的
   问题,设计必须已写进 risks 的"需要验证的点";没写 = finding,记
   `failure_readiness`。

## Severity 定义(critical_issues / review_findings 共用)

| 级 | 含义 |
|---|---|
| 🔴 BLOCKING | 照此开发必然返工/翻车,必须先解决 |
| 🔴 HIGH | 上线后高概率出事或显著浪费,交付前必须解决 |
| 🟡 MEDIUM | 特定条件下出事,应解决或明确接受为风险 |
| 🟢 LOW | 改进建议,不阻塞 |
