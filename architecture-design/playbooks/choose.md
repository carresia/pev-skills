# Playbook: choose(多方案选型)

在 2 个以上技术路线/方案之间选择,交付一份可辩护的选型决策。交付模板:`templates/decision.md`。

## 适用判断

用户给了选项("A 还是 B")、或开放地问"用什么做 X"且候选会显著影响架构形态。
**不是**所有技术选型都走这里——只影响局部、可逆的小选型(用哪个库)不值得一个
PEV 轮次,直接给建议并记 INFERENCE 即可。

## Plan 骨架

```text
1. survey_upstream    —— 提炼选型必须满足的硬约束与非功能性需求(NFR),即评估维度的来源
2. survey_codebase    —— 仅当现有代码库限制候选空间
3. design_options     —— 展开 ≥2 个候选(用户提供或 Executor 生成,生成须记 INFERENCE)
4. evaluate_options   —— 逐维评估矩阵,每维锚定上游 NFR/约束
5. draft              —— 推荐 + 代价 + 生效条件 + rejected_because
```

## Executor 要点

- **候选必须真实可辩**:不许故意弱化某个候选来给推荐项陪衬。每个候选按"如果它赢了,系统长什么样"展开
  到模块粒度,不是一行名字。落选候选的否决理由必须指向具体维度,不写"生态不如 A"。
- **每个候选必须写真实代价**(cost 非空,脚本强制):放弃什么、增加什么复杂度、
  谁为它买单。
- **评估维度锚定上游**:每条 criterion 标注它来自哪条 NFR/约束;与上游无关的维度
  (如"我个人更熟")不许进矩阵,可以进 recommendation.rationale 但必须明示权重
  来源(DECISION)。
- **推荐带失效条件**:写清"什么信号出现时应重新选型"(如用户量超过 X、上游新增
  强一致要求)。
- upstream_mapping 照填:每条 In Scope 条目在**推荐方案**下的落点(候选 id 或模块 id)。

## Verifier 检查重点(本场景加压项)

- 候选 ≥2,落选者是否也按赢家标准展开(有没有被故意弱化的陪衬候选)
- 评估维度是否全部锚定上游;有没有给推荐项暗中加权
- rejected_because 逐条成立吗,还是话术
- 推荐方案对 In Scope 的承载有没有缺口
