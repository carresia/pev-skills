# Database Schema Review Rubric

Verifier 评分判据。7 维各 1-5 分;PASS 要求全部 ≥3、逐库 verdict 全 PASS、
cross_review 通过、无 BLOCKING 发现、五门禁全绿。

## 分数通用定义

| 分 | 含义 |
|---|---|
| 5 | 该维度不仅合规,还给下游额外提供了可执行的确定性(如索引依据写到可直接转化为 EXPLAIN 验证用例) |
| 4 | 合规,无实质问题 |
| 3 | 合格底线:有交代但存在可改进处,不影响建库开工 |
| 2 | 有缺口,建库后会在此维度返工 |
| 1 | 缺失或错误,照此建库必然出错 |

## 七维判据

### 1. upstream_conformance(上游承接)
- 5:实体/数据流忠实承接,表条条回指实体,映射表可直接反查,交互语义与上游声明(幂等/一致性)一致
- 3:承接成立但个别表与实体的对应牵强(实体塞给不相关的库)
- 1:快照漏抄上游声明(分母造假)、私自扩边(上游外数据/跨模块共享表)、实体无落点、私挪数据所有权

### 2. schema_clarity(schema 清晰)
- 5:每张表单一目的可陈述,列类型无二义(金额/时间/长度/枚举值列全),主键策略带 WHY,约束显式(FK/UNIQUE/CHECK/NOT NULL + ON DELETE),方言与版本标注,命名见名知意且合规范
- 3:清晰成立但个别列语义含糊(枚举值未列全、长度无依据),或个别命名不见名知意
- 1:表目的说不清、主键策略缺失、约束停口号、方言含混、命名无意义或撞保留字

### 3. consistency(一致性)
- 5:命名、时间戳/审计列、状态枚举跨库统一,同一实体同名同义,ID 形态跨库一致或有映射交代
- 3:基本一致但存在个别库自造约定(时间戳一处 timestamptz 一处 bigint epoch)
- 1:同一概念跨库语义冲突、冗余数据无权威源、同类约束一处进库一处靠应用

### 4. compatibility(演进与迁移)
- 5:演进策略与兼容规则明确,什么算破坏性变更有定义,变更有回滚路径,锁影响有评估,大表有分区/归档交代
- 3:有策略但回滚路径含糊("出问题再回滚")
- 1:无演进交代、裸 ALTER 大表、不可逆 migration、分区缺失且无 accepted_risk

### 5. tradeoff_honesty(取舍诚实)
- 5:每条取舍的 cost 具体到"放弃了什么能力/承担了什么运维成本",替代方案有排除理由
- 3:取舍成立但个别 cost 是换汤话术("牺牲了一点性能")
- 1:关键决策(主键/选型/分区)无取舍记录、cost 为空话术、只写收益不写代价

### 6. simplicity(简单性)
- 5:schema 最小承接上游声明,每个横切列/分区方案/denorm/通用表名点可溯源的真实问题,更简单的形态被明确考虑并记录排除理由
- 3:复杂度有理由但个别论证牵强("未来可能要分库")
- 1:无问题背书的机制堆叠(没人查的表、无查询的索引);存在明显更简单的形态且无排除记录

### 7. traceability(溯源)
- 5:关键陈述条条有 Ledger 背书,FACT 指向上游产物/代码/DDL 可验证,DECISION 有拍板锚点,INFERENCE 依据链成立
- 3:主要决策有溯源,边缘陈述裸奔
- 1:上游声明无溯源、DECISION 无锚点、把推断写成事实

## 对抗 7 维定义(self_challenge 共用)

| 维度 | 攻击问题 |
|---|---|
| failure_modes | 约束缺失/级联误删/迁移翻车会怎么丢数据、造脏数据?旁路写入(绕过应用直连)会被什么挡住? |
| consistency | 同一数据在库内(冗余列)与跨库(读模型)怎么保持一致?违反了去哪查? |
| concurrency | 并发写入同一业务键(双提交、重试、重放)会撞什么?唯一键兜底了吗?乐观锁/热点页交代了吗? |
| boundary_erosion | 哪张表会变成下一个"谁都能写"的共享表?他模块会不会为了一次 JOIN 直连本库? |
| misuse_potential | 会走出哪条无索引的慢查询路径?软删除列会漏过滤吗?SELECT * / 分页深翻会踩什么坑? |
| compatibility | 哪个列/类型的变更需要锁表或重写?迁移回滚可行吗?大表变更窗口评估了吗? |
| simpler_alternative | 有没有实质上更小、同样承接上游声明的 schema(少一张表、少一个横切列、不分区)? |

## Cross 检查定义(全部库 PASS 后)

| 检查 | 攻击问题 |
|---|---|
| 命名与概念漂移 | 同一概念(状态枚举/时间戳/审计列约定)在各库定义一致吗? |
| ID 与键策略一致 | 同一实体的主键/业务键跨库形态一致吗?不一致处有映射交代吗? |
| 冗余数据权威源 | 同一数据多库各一份,谁是 source of truth、同步方向写明了吗? |
| 演进策略一致 | 各面的迁移风格/版本管理矛盾吗? |

## Severity 定义(critical_issues / findings / cross findings 共用)

| 级 | 含义 |
|---|---|
| 🔴 BLOCKING | 照此建库/迁移必然翻车(丢数据、锁死线上表),必须先解决 |
| 🔴 HIGH | 上线后高概率出事或显著浪费(无索引热查询、浮点存钱),交付前必须解决 |
| 🟡 MEDIUM | 特定条件下出事,应解决或明确接受为风险 |
| 🟢 LOW | 改进建议,不阻塞 |
