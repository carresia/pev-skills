# 实施流程指南

> SKILL.md 定协议,本文件放实施技法:基线、TDD 纪律、范围纪律、提交纪律、中断恢复、
> 常见借口对照。想不清楚某类任务怎么落成"先红后绿 + 可验证提交"时读这里。

## 基线(Before Anything)

开工前必答三件事,答案记入 Plan 的 `known` 与 artifact 的 `baseline`:

1. **分支与起点**:当前分支、HEAD commit(恢复与对账的锚点)。
2. **健康判据**:这个项目"没坏"怎么判?测试命令、构建命令、类型检查,真跑一遍。
3. **既有惯例**:命名、目录结构、测试框架——代码要长得像这个仓库写的,不是像模板写的。

基线检查 fail → 停:先修基线,或用户拍板调整检查口径(记 DECISION)。带着红基线
开工,结束时说不清哪些红是你造成的。

## 逐任务的 TDD 纪律

每条任务内部走红-绿-重构;测试技法细节见 `test-driven-development` skill。本 skill
的机器门禁管下限(done 必有通过的验证 + 证据),过程纪律在这里:

- **先红**:新逻辑先写会失败的测试;修 bug 先写复现测试(Prove-It:测试证明 bug
  存在,再修到它通过)。测试在 commit 里留下先红后绿的痕迹(测试与实现同 commit
  亦可,信息里注明)。
- **最小绿**:写让测试通过的最小实现。"简单优先":三行相似代码好过过早抽象;先写
  显然正确的笨版本,测试证明正确后再优化。
- **重构**:全绿前提下清理;每步重构后重跑测试。重构不与功能混进同一个 commit。
- **测什么**:测状态不测交互(断言结果,不断言内部调用序列);每测一个行为概念;
  测试名读起来像规格说明。真实现 > fake > stub > mock,只在边界(外部 API/发邮件)
  用 mock。
- **验证方式选择**:纯逻辑 → 单测;跨边界(API/DB/文件)→ 集成测试;关键用户流程
  → 少量端到端。声明 manual 的验证必须写看什么、什么算过。

## 范围纪律

`files_touched` 是上游清单声明的预计改动——执行时的比对基准,不是建议。

- **要动声明外的文件**:小牵连(如补一个导出、加一个类型)→ 记 deviations
  (path + why),继续。大牵连(改公共接口、动别模块的行为)→ 停,浮出三选一:
  这已经不是这条任务的活了。
- **发现声明与实际严重不符**(要动的文件根本不存在、真实改动是声明的三倍)→
  清单失实,unresolved 浮出,回 planning-and-task-breakdown;不默默按自己理解重排。
- **顺手加料是范围失控的开始**:"清理"相邻代码、改无关 import、"现代化"只读过的
  文件——都记 NOTICED 但不碰,浮出给用户决定(要修另行开任务)。

## 提交纪律

- **一任务一提交**(可拆为"实现 + 测试 + 重构"的少量语义完整提交);commit 信息
  说清做了什么、为什么。原子提交指引见 `git-workflow-and-versioning`。
- **不可逆操作单独成提交**:数据库迁移、删数据、改公共配置——单独 commit、单独
  可回滚;迁移提交配对回滚迁移。
- **批次末常绿**:每批结束构建与测试必须过;未完成功能用特性开关隔离,不把半成品
  暴露给主干。
- **新增代码默认安全**:新行为默认关闭(opt-in)、默认保守值;不删旧路径与加新路径
  混在同一个提交里。

## 中断恢复

PEV 实施记录的任务粒度就是恢复粒度:

1. 读 `impl/state.json` 与最新 artifact:哪些 done、哪些失败/延后、卡在哪。
2. 跑基线检查确认仓库起点没坏(坏了先处理再继续)。
3. 从第一条非 done 任务起继续;上游清单变了(WAITING_FOR_UPSTREAM 恢复)→ 只重排
   受影响批次,已 done 且不受影响的记录保留。
4. 恢复本身走 `playbooks/audit.md` 的审计流程先对账实况。

## 常见借口对照

| 借口 | 现实 |
|---|---|
| "最后一起测" | 第一片的 bug 会让后面每片都建在错误上;每片必测。 |
| "一次写完更快" | 出了问题在 500 行改动里找原因,比逐片验证慢得多。 |
| "这些改动太小,不值得单独提交" | 小提交免费;大提交藏 bug、难回滚。 |
| "回头再补测试" | 事后补的测试验证的是实现,不是行为。 |
| "我手动测过了" | 手动验证不持久;明天的改动悄悄弄坏它,无从知晓。 |
| "这个重构很小,顺手带上" | 功能混重构,两件事都难审难回滚;分开。 |
| "清单里少了个文件,我顺手改了" | 未声明改动就是范围违规(deviation 或回清单,二选一,没有第三种)。 |

## 红旗(出现即停并浮出)

- 写了 100 行以上代码没跑过测试
- 一个提交里混多件独立的事
- "我顺便也把…"的范围扩张
- 跳过验证步骤赶进度
- 批次之间构建/测试红着
- 大量未提交改动堆积
- 声明外的文件默默出现在 diff 里
