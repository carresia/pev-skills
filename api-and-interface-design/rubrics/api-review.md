# API Contract Review Rubric

Verifier 评分判据。7 维各 1-5 分;PASS 要求全部 ≥3、逐契约面 verdict 全 PASS、
cross_review 通过、无 BLOCKING 发现、五门禁全绿。

## 分数通用定义

| 分 | 含义 |
|---|---|
| 5 | 该维度不仅合规,还给下游额外提供了可执行的确定性(如错误语义写到可直接转化为契约测试用例) |
| 4 | 合规,无实质问题 |
| 3 | 合格底线:有交代但存在可改进处,不影响下游开工 |
| 2 | 有缺口,下游开工后会在此维度返工 |
| 1 | 缺失或错误,照此开发必然出错 |

## 七维判据

### 1. upstream_conformance(上游承接)
- 5:能力/交互忠实承接,操作条条回指能力,映射表可直接反查,交互语义与上游声明(同步/异步/幂等)一致
- 3:承接成立但个别操作与能力的对应牵强(能力塞给不相关契约面)
- 1:快照漏抄上游声明(分母造假)、私自扩边(上游外能力/新端点)、能力无落点、改写交互语义

### 2. contract_clarity(契约清晰)
- 5:每个操作单一目的可陈述,请求/响应无二义(空值/时区/ID 形态/分页边界都定义),隐性契约(排序/时序)被有意承诺或明确不承诺
- 3:清晰成立但个别字段语义含糊(枚举值未列全)
- 1:操作目的说不清、同一响应形态随条件变化、分页边界二义

### 3. consistency(一致性)
- 5:命名、错误模型、分页/时间戳约定跨契约面统一,同一概念同名同义
- 3:基本一致但存在个别面自造约定(时间戳一处 ISO 一处 epoch)
- 1:错误语义混用(有的抛异常有的返回包裹体)、同一概念跨面语义冲突

### 4. compatibility(兼容与演进)
- 5:版本策略与兼容规则明确,破坏性变更有弃用路径,新增字段为可选加法,幂等有交代
- 3:有策略但弃用路径含糊("下线前通知")
- 1:无版本与兼容交代、存在无声破坏性变更、上游标幂等的交互契约未处理重复

### 5. tradeoff_honesty(取舍诚实)
- 5:每条取舍的 cost 具体到"放弃了什么能力/承担了什么消费方复杂度",替代方案有排除理由
- 3:取舍成立但个别 cost 是换汤话术("牺牲了一点灵活性")
- 1:关键契约决策无取舍记录、cost 为空话术、只写收益不写代价

### 6. simplicity(简单性)
- 5:接口面最小承接上游声明,每个版本机制/通用包裹字段/批量端点名点可溯源的真实问题,更小的接口面被明确考虑并记录排除理由
- 3:复杂度有理由但个别论证牵强("未来可能需要")
- 1:无问题背书的机制堆叠;存在明显更小的接口面且无排除记录;多契约面重复暴露同一能力且语义冲突

### 7. traceability(溯源)
- 5:关键陈述条条有 Ledger 背书,FACT 指向上游产物/代码可验证,DECISION 有拍板锚点,INFERENCE 依据链成立
- 3:主要决策有溯源,边缘陈述裸奔
- 1:上游声明无溯源、DECISION 无锚点、把推断写成事实

## 对抗 7 维定义(self_challenge 共用)

| 维度 | 攻击问题 |
|---|---|
| failure_modes | 每个操作的失败路径(依赖挂/超时/重复调用)有错误契约吗? |
| consistency | 同一资源在契约不同处(读/写/事件)的状态语义一致吗? |
| concurrency | 并发/重复调用(双提交、重放)契约怎么回答?幂等交代了吗? |
| boundary_erosion | 哪个契约面会积累操作成为下一个"什么都有的"巨型接口? |
| misuse_potential | 哪里会被消费者依赖成隐性契约(排序/时序/文案/字段顺序)? |
| compatibility | 哪个字段/行为的变更会破坏现有消费者?弃用路径在哪? |
| simpler_alternative | 有没有实质上更小、同样承接上游声明的接口面? |

## Cross 检查定义(全部契约面 PASS 后)

| 检查 | 攻击问题 |
|---|---|
| 错误语义统一 | 各契约面的错误模型矛盾吗? |
| 命名与概念漂移 | 同一概念(状态枚举/字段语义/分页与时间戳约定)在各契约面定义一致吗? |
| 版本策略一致 | 各契约面的版本策略矛盾吗? |
| 能力重复暴露 | 同一能力在多个契约面重复暴露且语义冲突?权威源是谁? |

## Severity 定义(critical_issues / findings / cross findings 共用)

| 级 | 含义 |
|---|---|
| 🔴 BLOCKING | 照此开发必然返工/翻车,必须先解决 |
| 🔴 HIGH | 上线后高概率出事或显著浪费,交付前必须解决 |
| 🟡 MEDIUM | 特定条件下出事,应解决或明确接受为风险 |
| 🟢 LOW | 改进建议,不阻塞 |
